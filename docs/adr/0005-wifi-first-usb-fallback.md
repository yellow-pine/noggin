# Links are Wi-Fi first, USB second; every Core is addressed directly

The Mech should sit on the desk untethered: pack-powered, with no cable to the Mac. Both Cores join the home Wi-Fi as stations (Bambu's MicroPython build has `network.WLAN` and `espnow`; Bluetooth and WebREPL are removed, see docs/research/2026-10-31-radio.md). The noggin service talks to each Core directly, so no relay firmware exists. Each Core sends a UDP beacon every 2 s (`noggin <name> <ip> <uptime s>`); the service listens on one port and learns the Cores from it. Commands are the existing newline command lines, one per UDP datagram, as `<tag> <seq> <line>`: the tag is an HMAC-SHA256 of `<name> <seq> <line>` under the shared token (the token itself never travels, and a datagram for one Core is worthless to another), the sequence is milliseconds since the epoch and must never go backwards (replays are dropped); the Core answers with a one-line ack from its own address and command port on receipt, before it runs the line (a gesture takes about a second, longer than the ack window), and the service retries once after 200 ms. The Core keeps its radio out of power save (`wlan.config(pm=wlan.PM_NONE)`): in power save the access point holds its datagrams for a DTIM or more. Beacons are unauthenticated discovery: the service trusts only the datagram's source address, never the claimed one. Wi-Fi credentials and the token are written once over USB by the setup wizard (`wifi.json` beside `calibration.json`). USB-C keeps two jobs: flashing (mpremote, the only path, there is no over-the-air update) and an automatic fallback Link when the radio is down or a line goes unacked over Wi-Fi. Offline Cores make hooks silent no-ops; the service reconnects on its own and `noggin status` shows wifi / usb / offline per Core. Each Core reports its uptime since power-on, the only battery signal available (the shield has no voltage sense); one pack per shield, the spare swapped in.

## Known limits

Accepted as-is: `send` blocks the service loop up to 400 ms per unacked line (two tries of 200 ms); a datagram that never reached the Core could be replayed by a third party until the Core sees a higher seq; an ack means received, not run: a parser exception follows as a second reply, `err <seq> <reason>`, which the service does not wait for (an unknown command is a silent `ok`); a Core busy with a gesture acks the next line only when it is done, so that line goes unacked on Wi-Fi; over Wi-Fi a batch stops at the first unacked line and the rest goes over USB when the cable is in, else is logged as dropped; a lost ack sends that line over USB too, so it can run twice, and a socket error on Wi-Fi resends the whole batch over USB, lines already acked included; beacons are unauthenticated, so the source address is trusted as the Core's; the USB fallback assumes the eyes Core (`USB_CORE` in noggin/service.py).

## Considered options

- Core 1 relays to Core 2 by ESP-NOW: rejected once both Cores can be on the LAN; one more protocol for nothing.
- Bluetooth LE from the Mac: rejected, the Bambu build has no `bluetooth` module.
- ESP-NOW through a third Core as USB dongle: rejected, it keeps a cable and adds a part.
- mDNS names: unverified on the Bambu build; the beacon needs nothing from the network.
- TCP: rejected for now; datagrams plus one retry cover one-line commands with less reconnection logic.
- Two packs in series for runtime: impossible, 14.8 V exceeds the shield's 12.6 V input.
