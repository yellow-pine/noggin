# Links are Wi-Fi first, USB second; every Core is addressed directly

The Mech should sit on the desk untethered: pack-powered, with no cable to the Mac. Both Cores join the home Wi-Fi as stations (Bambu's MicroPython build has `network.WLAN` and `espnow`; Bluetooth and WebREPL are removed, see docs/research/2026-10-31-radio.md). The noggin service talks to each Core directly, so no relay firmware exists. Each Core sends a UDP beacon every 2 s (`noggin <name> <ip> <uptime s>`); the service listens on one port and learns the Cores from it. Commands are the existing newline command lines, one per UDP datagram, as `<tag> <seq> <line>`: the tag is an HMAC-SHA256 of `<name> <seq> <line>` under the shared token (the token itself never travels, and a datagram for one Core is worthless to another), the sequence is milliseconds since the epoch and must never go backwards (replays are dropped); the Core answers with a one-line ack from its own address and command port on receipt, before it runs the line (a gesture takes about a second, longer than the ack window), and the service tries each line up to four times, waiting 0.2, 0.4, 0.8 and 1.6 s for the ack, with the same seq (the Core re-acks its highest seq without running it again). The Core keeps its radio out of power save (`wlan.config(pm=wlan.PM_NONE)`): in power save the access point holds its datagrams for a DTIM or more. Beacons are unauthenticated discovery: the service trusts only the datagram's source address, never the claimed one. Wi-Fi credentials and the token are written once over USB by the setup wizard (`wifi.json` beside `calibration.json`). The eye program is flashed over the same Link (`make flash` while the beacon is fresh, issue #108): `put <file> <offset> <base64>` lines of 120 bytes each (the datagram stays inside the Core's 256-byte read) append to `<file>.new`, and `commit <file> <sha256>` swaps it in only if the hash matches, keeping the old file as `<file>.bak` and listing it in `flash.trial`; both are answered once they ran, `ok` or `err`, not on receipt. Then `reboot`; boot.py gives the new program 10 s to reach `noggin ready` and otherwise puts the .bak files back and reboots, and the service, once the beacon is back, sends the same commits again: ok only while the Core runs the new files. boot.py itself never goes over Wi-Fi. So USB-C is recovery only: boot.py and the first install (mpremote, `USB=1 make flash`), whatever Wi-Fi cannot fix, and the automatic fallback Link when the radio is down or a line goes unacked over Wi-Fi. Offline Cores make hooks silent no-ops; the service reconnects on its own and `noggin status` shows wifi / usb / offline per Core. Each Core reports its uptime since power-on, the only battery signal available (the shield has no voltage sense); one pack per shield, the spare swapped in.

## Known limits

Accepted as-is: `send` blocks the service loop up to 3 s per unacked line (four tries), so a Core that vanished while its beacon is still fresh (up to 6 s) stalls a batch 3 s a line; a datagram that never reached the Core could be replayed by a third party until the Core sees a higher seq; an ack means received, not run: a parser exception follows as a second reply, `err <seq> <reason>`, which the service does not wait for (an unknown command is a silent `ok`); a Core busy with a gesture acks the next line only when it is done, so a gesture longer than the 3 s of ack windows leaves that line unacked on Wi-Fi; an unacked line does not stop its batch: the rest still goes over Wi-Fi, and the unacked lines follow over USB when the cable is in (after the batch, so out of order), else are logged as dropped; a lost ack sends that line over USB too, so it can run twice, and a socket error on Wi-Fi resends the whole batch over USB, lines already acked included; beacons are unauthenticated, so the source address is trusted as the Core's; the USB fallback assumes the eyes Core (`USB_CORE` in noggin/service.py); a flash blocks the service loop until it is done (up to a minute); a commit that fails after earlier files were swapped in leaves a mix until the next flash (the hash checks make it unlikely); the fallback catches a program that raises or hangs in Python before `noggin ready`, not one that crashes after it or hangs inside C; a Core still running a wifi.py from before #108 acks every `put` on receipt, so the first flash with it goes over USB.

## Considered options

- Core 1 relays to Core 2 by ESP-NOW: rejected once both Cores can be on the LAN; one more protocol for nothing.
- Bluetooth LE from the Mac: rejected, the Bambu build has no `bluetooth` module.
- ESP-NOW through a third Core as USB dongle: rejected, it keeps a cable and adds a part.
- mDNS names: unverified on the Bambu build; the beacon needs nothing from the network.
- TCP: rejected for now; datagrams plus retries cover one-line commands with less reconnection logic.
- Two packs in series for runtime: impossible, 14.8 V exceeds the shield's 12.6 V input.
